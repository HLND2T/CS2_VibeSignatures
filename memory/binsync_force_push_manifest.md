# BinSync push manifest + fork-only force_push_all

## Purpose
`push_binsync_symbols.py` + `headless_force_push.py` prepare per-binary BinSync changes against isolated local sinks. The self-hosted build never pushes canonical refs; `binsync_candidate.py` packages the local commits, a hosted verifier checks the candidate, and the protected `binsync_publish.py` publisher performs allowlisted fast-forward publication. Originally `headless_force_push.py` did a `collect_artifacts` dump of **every** function/global/type/segment in the IDB — for engine2.dll that was 789 functions + 394 comments, and ~16k artifacts for big modules (scenesystem = 37k), making the step take minutes and bloating remotes with auto-named (`sub_*`/`unknown_libname_*`/`HandlerRoutine`) junk and IDA auto-comments (`Microsoft VisualC v7/14 64bit runtime`, `Trap to Debugger`, stack-var arg names).

## Fix: manifest-driven selective push
- `push_binsync_symbols.collect_manifest_symbols(root, gamever, config)` walks `configs/{gamever}.yaml` `modules[].symbols[]`, keeps only `category` in {`func`,`vfunc`,`gv`}, and reads the target address from tracked `bin_artifacts/<gamever>/<module>/{symbol}.{platform}.yaml` — `func_rva` for funcs/vfuncs, `gv_rva` for globals. These are already in BinSync's lifted/RVA form (Windows rva = va - 0x180000000; Linux rva == va). Output: `{"module/platform": {"functions":[int], "globals":[int], "names": {str(rva): symbol}}}`. `names` lets `headless_force_push.apply_manifest_names` promote bare-code addresses (`idaapi.add_func`) and rename only IDA-auto names (`sub_`/`loc_`/`unk_`/…) to their canonical symbol, so a release that skips the `-rename` post-process pass still publishes canonical BinSync names.
- Per binary, it writes a temp JSON manifest and invokes `headless_force_push.py <bin> --push --artifacts-file <manifest>`.
- `headless_force_push.py` gained `--artifacts-file`; when set it calls `controller.force_push_all(func_addrs, global_addrs, [], [], use_decompilation=...)` — i.e. **empty types and segments**.
- Symbols whose YAML has no `func_rva`/`gv_rva` are skipped. This is correct and expected: 55 engine Windows `vfunc`-category symbols are vtable-slot-only (only `vfunc_sig` + `vfunc_index`, e.g. `ISource2GameClients_ClientSettingsChanged`) and cannot be pushed as standalone functions.
- Real 14174 counts: 1839 functions + 733 globals across 16 binaries (vs. full-dump).

## Windows lift bias (CRITICAL: declib first-segment base != PE image base)
YAML `*_rva` = `va - image_base` (0x180000000 for these PEs; 0 for ELF). But declib's `binary_base_addr` = `get_first_segment_base()` = **lowest-address IDA segment VA** — for a PE that's `.text` at `image_base + first_section_rva` (0x1000), NOT the image base. So declib's lifted function/global key = `va - (image_base + 0x1000)` = `rva - 0x1000` on Windows, while on Linux (ELF loads at vaddr 0) key == `rva`. **The manifest MUST send `rva - first_section_rva` on Windows** or BinSync's `_collect_force_push_functions`/`_collect_force_push_globals` silently skip almost everything (engine2.dll went from 256 → 14 funcs, 115 → 8 globals; networksystem.dll 27 → 0). Fix lives in `push_binsync_symbols.py`: `_pe_first_section_rva()` parses the PE section table, `_first_segment_lift_bias(binary_path)` returns 0x1000/0 for PE/ELF, and `collect_manifest_symbols` subtracts the bias from each YAML `*_rva`. A handful of funcs matched pre-fix because their IDB `start_ea` had been offset +0x1000 (IDB shows `sub_1800A0ED0` for YAML va `0x18009fed0`), coincidentally canceling the bias.

## Fork-only API (critical gotcha)
`BSController.force_push_all(func_addrs, global_addrs, type_names, segment_names, use_decompilation)` **only exists in the HLND2T/binsync fork** (commit e229614 "Add force_push_all single-commit helper"), NOT in upstream `binsync/binsync` nor PyPI `binsync==5.15.3`. Upstream/pypi only have `force_push_functions`, `force_push_global_vars`, `force_push_types`, `force_push_segments` (each its own commit). `force_push_all` collects funcs + their contained comments (via `_force_push_function_comments`) + globals + types + segments into ONE commit. The self-hosted runner's standalone `python` interpreter (the `--python` passed to `push_binsync_symbols.py`) MUST have the HLND2T fork installed from source (see `docs/en/requirements.md`), or `force_push_all` raises AttributeError.

## Comments: no user/auto flag available
The `Comment` artifact (declib 4.5.0) has only `addr/comment/func_addr/decompiled` — `decompiled` tracks the IDA comment *slot* (hexrays user cmt vs disasm/function-header cmt), NOT whether the text is user-authored vs IDA-auto. Auto-comments (`Microsoft VisualC ... runtime`, `switch jump`, stack-var names from decompiler) are mixed with real ones in `deci.comments`, so the current manifest approach still pushes auto-comments for the selected functions. Truly filtering IDA-auto comments is not possible through this API; it would need IDA-side classification. The big win already comes from (a) dropping types+segments and (b) pushing only declared functions rather than the whole IDB.

## Involved files

## Issue #947: bootstrap local-init mode (2026-09-08)
New-GAMEVER bootstrap runs `warmup-idb --binsync skip`, but `push_binsync_symbols.py --prepare-only` unconditionally cloned the canonical BinSync remote when the local `.bsproj` was missing — the canonical remotes for a brand-new GAMEVER do not exist yet, so clone failed (surfaced as proxy 502 via the HZVM:8080 system insteadOf rewrite). Fix (explicit mode, never implicit on `--no-publication-candidate`):
- `push_binsync_symbols.py --bootstrap-local-init`: missing `.bsproj` repos are initialized locally via `initialize_minimal_binsync_repo()` + `git remote add origin <canonical>`; `_remote_heads()` is never called; snapshots carry `remote_url` only (no `heads`). `assert_remote_refs_unchanged` hard-fails on snapshots without heads (remote mode unchanged). Evidence: `local-evidence.json` gets `binsync_mode: "bootstrap-local-init"` and `initialized_locally: true` per repo; `remote_refs_*_sha256` = digest of the empty ref set (`BOOTSTRAP_LOCAL_INIT_REFS_DIGEST`). CLI requires `--no-publication-candidate` (local-init results are never publication candidates).
- `headless_force_push.py --bootstrap-local-init` (with `--push --local-only`): the bare sink is cloned from the local repo itself instead of the canonical remote, and canonical-remote ls-remote before/after checks are skipped. Origin is still required to match the canonical URL (TRUSTED_REMOTE_RE).
- Workflow gate-evidence schema v2 is UNCHANGED (`binsync_mode: "local-only"`, before==after digests) on purpose: the hosted verifier `new_gamever_artifact.py` runs from the trusted base SHA, so schema changes would not be visible to this PR's publish job.
- Canonical remote creation stays in the protected `init_gamebin.py --binsync enable --create-missing-binsync-remotes` stage (not wired into bootstrap). A lighter, binary-free equivalent for CI is `init_gamebin.py ensure-binsync-remotes <gamever> --user release-automation`, which reads md5 from tracked `binary_locks/<gamever>.json`; the protected `rebuild-free-release.yml` workflow runs it on `ubuntu-latest` before a tracked-artifact release.
- Tests: `TestBootstrapLocalInit` (test_push_binsync_symbols.py) + bootstrap sink tests (test_headless_force_push.py); verified end-to-end with real git (init → sink push → origin restore, no network).


### Issue #951: availability probe must cover every per-module remote (2026-09-09)
`init_gamebin.py check-binsync` used to check only the environment (gh present/authenticated, API reachable, `HLND2T` org visible), so a brand-new GAMEVER probed "available", the operator opted in, and `prepare --binsync enable` then hard-failed in `preflight_binsync` ("BinSync remote repository ... does not exist") — while the skill requires a manual-flow missing remote to skip gracefully.
- `probe_binsync(root, config_path=None, gamever=None, *, require_remotes=True)`: with a `gamever` it enumerates the configured binaries and requires every `HLND2T/CS2_VibeSignatures_binsync_<gamever>_<module>` to exist **and be public** (one `gh api repos/...` per repo, `allow_404=True`; `private is not False` mirrors `inspect_remote`). Still never raises: `AnalysisConfigError`, non-404 `gh_api` failures, and invalid metadata all return `(False, reason)`. Without a gamever the behavior is the pre-#951 environment-only probe.
- Empty remotes stay "available" on purpose: `prepare` restores them from local `binsync/*` branches (the #947 bootstrap-local-init path), so absence of branches is not an availability problem.
- `require_remotes=False` is passed by `prepare` when `--create-missing-binsync-remotes` is set (trusted CI may create them); the flag therefore still works, and the manual skill path (`check-binsync <GAMEVER>`) is the one that pre-rejects missing remotes.
- Enabling this without downloading binaries required `iter_configured_binaries(..., require_existing=False)` (skips the `is_file` gate but keeps module order, path dedupe, and filename-collision rejection); `binsync_repo_name()` now owns the repo-name format shared by the probe and `expected_sidecar`.


### Follow-up: insteadOf expansion broke origin validation (PR #948 review)
`git remote get-url` expands `url.*.insteadOf` (documented behavior), so under the #927 system-level proxy rewrite it returned `http://HZVM:8080/...` and the canonical-origin checks rejected valid repos: `validate_local_binsync_repo` (init_gamebin), `local_only_remote` (headless_force_push), and the publish-path check (binsync_candidate `_collect` ~line 792). Fix: all three read the raw stored value via `git config --get remote.origin.url` (never expanded). Regression tests inject the rewrite through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` env (propagates to child git processes, no system config needed) and assert both the premise (`get-url` returns the proxy URL) and that validation/build passes. Note: `.claude/skills/trigger-release-build` also uses `git remote get-url` for repo identity but runs on operator machines, not the proxied CI runner — left unchanged.
